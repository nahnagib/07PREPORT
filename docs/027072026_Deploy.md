# VPS Deployment Guide — 07 Ps Sales Dashboard

Written 2026-07-27, after a full pre-deployment audit of the repo. Target: the IT-provisioned VPS
for the same deployment this repo's existing docs describe (Libyan Spider VPS, Docker Compose,
domain `benmussa-invest.com` used as the placeholder throughout — replace with the real domain).

**This doc is the accurate, verified baseline.** [`07ps-sales-dashboard-app/docs/vps-deployment.md`](../07ps-sales-dashboard-app/docs/vps-deployment.md)
says the same thing and matches the real `docker-compose.yml` — treat the two as consistent. Do
**not** follow [`07ps-sales-dashboard-app/docs/libyan-spider-deployment.md`](../07ps-sales-dashboard-app/docs/libyan-spider-deployment.md)
literally: it predates the current architecture and gets the database name/user wrong throughout
(`ps_warehouse`/`ps_app` — the real database is `powerBI_Data`, confirmed live against this
session's dev environment) and incorrectly claims migrations auto-run on startup. It's kept for its
useful checklist/troubleshooting structure, not as a source of DB facts.

---

## 0. Before you start: two things that will break a fresh deploy if skipped

These came out of this session's audit and aren't obvious from the other docs:

1. **Only apply migrations `0009_auth_identity.sql` through `0013_role_data_scope.sql`.** Do not
   run `data/warehouse/apply_migrations.py` unmodified against the real database. Files
   `0001`–`0008` build a second, dead schema (`dim_company`, `fact_order`, a bare-shape `app_user`,
   etc.) this app never queries — and worse, `0006_platform_rbac.sql`'s plain `CREATE TABLE
   app_user` (6 columns, no `password_hash`) will silently block `0009`'s `CREATE TABLE IF NOT
   EXISTS app_user` (the real 20-ish column auth shape) from ever creating the correct table,
   because `IF NOT EXISTS` is a no-op once the table exists in *any* shape. That leaves `app_user`
   missing `password_hash`/`status`/`role_id`, and `createAdmin.ts` fails with `Unknown column
   'password_hash'`. See §4 for the exact safe procedure.
2. **The real sales data isn't created by any migration.** `Dim_Company`, `Fact_SalesLines`,
   `Fact_Opportunity`, etc. (the tables every chart actually queries) are created and populated
   dynamically by the Python ETL pipeline's `DatabaseExporter` the first time a full run executes
   against live Odoo — not by a schema file. Budget ~55–60 minutes for this (§5).

## 1. Prerequisites on the VPS

Versions below are what this repo is built/tested against (from `package.json` engines, Dockerfiles,
and `data/etl/requirements.txt` — not generic recommendations):

| Requirement | Version | Why |
|---|---|---|
| OS | Ubuntu 22.04+ | matches `docs/vps-deployment.md` / Dockerfile base images |
| Docker Engine | 24.0+ | runs the whole stack via Compose |
| Docker Compose | 2.20+ (the `docker compose` plugin, not the standalone v1 binary) | `docker-compose.yml` uses `version: '3.9'` syntax |
| Node.js | 20+ | `backend`/`frontend` — matches `backend/Dockerfile`'s base image and `next dev`/`next build`'s Next.js 14.2.5 requirement |
| Python | 3.11 | `data/etl/Dockerfile.api` base image; the vendored pipeline is validated against 3.11 specifically |
| Nginx | 1.24+ (Ubuntu repo default is fine) | reverse proxy + TLS termination, runs on the **VPS host**, not in Docker |
| Certbot | with the Nginx plugin | Let's Encrypt TLS |
| MySQL 8 | external, **not containerized** | `docker-compose.yml` has no `mysql` service on purpose — this app connects to an existing MySQL 8 instance (see `docs/tech-stack-decision.md` §3 for why) |
| git, curl, openssl | — | cloning + secret generation |

```bash
ssh root@<VPS_IP>
apt-get update && apt-get upgrade -y
curl -fsSL https://get.docker.com -o get-docker.sh && sh get-docker.sh
apt-get install -y nginx certbot python3-certbot-nginx git curl openssl
```

**Resources**: 4 vCPU / 8GB RAM / 100GB SSD recommended (2 vCPU / 4GB / 50GB is the hard minimum —
the nightly full ETL refresh and concurrent dashboard users both need headroom).

## 2. Clone and configure

```bash
mkdir -p /opt/07ps-dashboard && cd /opt/07ps-dashboard
git clone <this-repo-url> .
cd 07ps-sales-dashboard-app
```

Before doing anything else, confirm the clone is actually complete — this repo had 28 untracked
files (including load-bearing source) discovered and committed during this session's audit; if
you're cloning from *before* that fix landed, `docker compose build` will fail on missing modules.
Sanity check:

```bash
test -f backend/src/services/dataScopeService.ts && echo "OK: repo includes the post-audit commit"
```

### Environment files — copy from `.example`, fill in real values (never commit the results)

```bash
cp backend/.env.example backend/.env
cp data/etl/.env.example data/etl/.env
cp data/ingestion/.env.example data/ingestion/.env   # optional side sandbox, not required to run the app
```

Full variable reference (names only — see each `.env.example` for inline docs, never copy example
values into production):

**`backend/.env`** — `PORT`, `DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME`/`DB_SOCKET`,
`JWT_SECRET`, `FRONTEND_ORIGIN`, `SMTP_*`, `RATE_LIMIT_*`/`ACCOUNT_LOCK_THRESHOLD`/
`PASSWORD_RESET_TOKEN_TTL_MIN`, `ETL_API_URL`/`ETL_API_KEY`/`ETL_API_POLL_INTERVAL_MS`/
`ETL_LOG_DIR`, `ETL_SCHEDULE_INCREMENTAL_CRON`/`ETL_SCHEDULE_INCREMENTAL_ENABLED`/
`ETL_SCHEDULE_FULL_CRON`/`ETL_SCHEDULE_FULL_ENABLED`, `REDIS_HOST`/`REDIS_PORT`,
`PUPPETEER_EXECUTABLE_PATH` (only relevant outside Docker — the container image already has Chromium).

**`data/etl/.env`** — `DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME` (same MySQL instance,
reuse the same values as `backend/.env`), `ODOO_URL`/`ODOO_DB`/`ODOO_USER`/`ODOO_API_KEY`,
`ODOO_TIMEOUT_SECONDS`/`ODOO_MAX_RETRIES`, `TIMEZONE`, `INPUT_DIR`/`OUTPUT_DIR`, `ETL_API_KEY`,
`LOG_LEVEL`, `FLASK_ENV`, `PYTHON_BIN`.

Things worth getting right the first time:

- **`DB_NAME` must be set explicitly in both files.** Three places in the codebase
  (`backend/.env.example`, `backend/src/db/pool.ts`, `apply_migrations.py`) default to the wrong,
  stale `ps_warehouse` if left unset. Use the real database name (`powerBI_Data` in this
  environment's dev instance — confirm the production DB's actual name with whoever owns it).
- **`ETL_API_KEY` must be identical** in `backend/.env` and `data/etl/.env` — it's the Bearer token
  the backend/etl-worker use to authenticate to the Flask ETL API. Generate one value, paste it in
  both files: `openssl rand -base64 32`.
- **`JWT_SECRET`**: also `openssl rand -base64 32`. Rotating it later invalidates every existing
  session.
- **`FRONTEND_ORIGIN`**: the real frontend origin (`https://benmussa-invest.com` or your domain) —
  this is the CORS allow-list (`backend/src/server.ts:28`), comma-separated if you need more than
  one origin. It already defaults to `localhost:3000` only, never wide-open (`*`) — just make sure
  it's actually set for prod, or the frontend can't call the API at all.
- **`NEXT_PUBLIC_API_BASE_URL`** is not a backend var — it's read by the frontend
  (`frontend/src/lib/api.ts:11`) and gets **inlined into the client bundle at `next build` time**,
  not read at container start. Set it before building, either exported or edited directly in
  `docker-compose.yml`:
  ```bash
  export NEXT_PUBLIC_API_BASE_URL=https://api.benmussa-invest.com
  ```
  (Ignore `NEXT_PUBLIC_API_URL` if you see it anywhere — it's a stale/unused variable name that
  doesn't match what the frontend code actually reads.)
- **`basePath`**: `frontend/next.config.mjs` sets `basePath: '/Dashboard'` — the app is designed to
  be served under a `/Dashboard` path prefix, not the domain root. `docker/nginx.conf` (§7) already
  accounts for this (redirects `/` → `/Dashboard`, proxies `/Dashboard/*` through) — no action
  needed unless `basePath` is removed from `next.config.mjs` in the future.

## 4. Database migrations — fresh DB, in order, including seed data

**Only files `0009` through `0013`.** Confirm your MySQL 8 database exists (or let the first
statement create it) and is reachable, then apply the five real, idempotent migrations in order —
each is safe to re-run (`CREATE TABLE IF NOT EXISTS` / `INSERT IGNORE` throughout):

```bash
mysql -h <DB_HOST> -P <DB_PORT> -u <DB_USER> -p <DB_NAME> < data/warehouse/migrations/0009_auth_identity.sql
mysql -h <DB_HOST> -P <DB_PORT> -u <DB_USER> -p <DB_NAME> < data/warehouse/migrations/0010_etl_admin_page.sql
mysql -h <DB_HOST> -P <DB_PORT> -u <DB_USER> -p <DB_NAME> < data/warehouse/migrations/0011_etl_control_center.sql
mysql -h <DB_HOST> -P <DB_PORT> -u <DB_USER> -p <DB_NAME> < data/warehouse/migrations/0012_pipeline_pages.sql
mysql -h <DB_HOST> -P <DB_PORT> -u <DB_USER> -p <DB_NAME> < data/warehouse/migrations/0013_role_data_scope.sql
```

Do **not** run `python data/warehouse/apply_migrations.py` unmodified — it walks every `.sql` file
in the folder including `0001`–`0008`, which causes the `app_user` shape conflict described in §0.
If you'd rather use the script, temporarily move `0001`–`0008` out of the `migrations/` folder
first, run the script, then move them back (they're kept in the repo for history, not for
execution against the real warehouse).

**Seed data — no separate seeder needed.** `0009_auth_identity.sql`'s own `INSERT IGNORE`
statements seed:
- `role_tier` (the 6 BI scope tiers) and `roles` (ADMIN, GCEO, GCFO, GCCO, GCTO, TIKA_CEO,
  B2B_DIRECTOR, B2C_DIRECTOR, SALESPERSON)
- `pages` and `permissions` (one row per page × view/export)
- The default `role_permissions` grant matrix (Admin gets everything; the executive/director roles
  get view+export on every Sales page; Salesperson gets view-only)

`0012` adds the `pipeline_health`/`pipeline_trend`/`activity_momentum` pages to that same matrix.
`0013` adds one `role_data_scope` row scoping `B2B_DIRECTOR` to `segmentKeys=1` (Customer Group =
B2B) — this is the row-level filter feature verified live this session; confirm it after deploy
(§8).

**First Admin account** — fully non-interactive, safe to script (verified by reading
`backend/scripts/createAdmin.ts` directly):

```bash
cd backend
npm run create-admin -- --email=admin@yourdomain.com --fullName="Your Name" --password='Str0ngPass!'
# --password is optional -- omit it and a random temp password is generated and printed,
# with the account forced into a must-change-password state on first login.
```

This requires `0009_auth_identity.sql` to already be applied (it looks up the `ADMIN` role and
fails with a clear error if the role table is empty) — nothing else.

**The real sales data (`Dim_Company`, `Fact_SalesLines`, `Dim_Segment`, `Fact_Opportunity`, etc.)
is not created by any of the above.** It's created and populated by the ETL pipeline itself, the
first time a full run executes — see §5.

## 5. Redis and the ETL worker in production — Docker Compose

**Decision already made and built, not open**: this repo already ships a working
`docker-compose.yml` at the repo root defining every long-running process this app needs, with
health checks and correct internal DNS already wired up. There's no pm2/systemd variant to choose
between — Compose is the established path (confirmed against the real file, not a guess):

```yaml
services:
  redis:        # BullMQ queue backend — the only thing Redis is used for in this app
  etl-api:      # Flask, gunicorn -w 1, wraps the Python pipeline — the only container with Python installed
  backend:      # Express API + registers the two cron schedules (ticks just enqueue jobs)
  frontend:     # Next.js, `next start`
  etl-worker:   # Node-only BullMQ worker — consumes the queue, calls etl-api over HTTP
  ingestion:    # standalone Python ingestion sandbox, optional
```

Three processes matter beyond the obvious backend/frontend:

- **Redis** — required for ETL scheduling/queueing. If unreachable, the backend no longer crashes
  (a fix already in place: `etlQueue.ts` attaches an error listener + a 10s enqueue timeout), but
  no ETL run — scheduled or manual — can be processed until it's back.
- **`etl-worker`** — a second, independent Node process. The cron schedules registered inside the
  main `backend` process only *enqueue* jobs; nothing executes them without this running. A queued
  job with no worker auto-fails after ~10 minutes with a clear error in Admin → ETL Runs.
- **`etl-api`** (Flask/gunicorn) — the only container with Python + the vendored pipeline
  installed. `etl-worker` calls it over HTTP for every run; it isn't optional even for a single
  manual trigger.

Build and start everything:

```bash
docker compose build
docker compose up -d
docker compose ps          # wait for all services to report "healthy"
```

`etl-worker` and `ingestion` have no HTTP health check (nothing to check) — confirm via logs
instead: `docker compose logs etl-worker` should show it connecting to Redis without errors.

**Run the first full ETL refresh** (creates every `Dim_*`/`Fact_*` table from live Odoo data —
this is the step that actually makes the dashboard show real numbers, budget ~55–60 minutes):

```bash
docker compose exec backend npm run etl:full -- --sync
```

Or trigger it from the Admin UI (Admin → ETL Runs → Trigger Full Refresh) once the app is up.

## 6. Building and starting backend and frontend in production mode

Already verified this session — both build cleanly:

```bash
# Backend: tsc compile, no watch
cd backend && npm run build && npm start     # node dist/server.js

# Frontend: production Next.js build, no dev/hot-reload flags
cd frontend && npm run build && npm start    # next start (NOT `next dev -H 0.0.0.0` — that's dev-only)
```

Under Docker Compose this is already what each `Dockerfile`'s `CMD` does (`backend/Dockerfile`:
`npm start`; `frontend/Dockerfile`: builds then `npm start`; `backend/Dockerfile.etl-worker`: `node
dist/etl/commands/worker.js`) — `docker compose build && docker compose up -d` (§5) is the actual
production path; the commands above are for confirming a build works outside Docker, e.g. in CI.

**A known resilience gap, not fixed here per this session's scope**: there is no
`process.on('unhandledRejection', ...)`/`uncaughtException` handler anywhere in `backend/src`. An
uncaught async rejection outside a route's own `try/catch` (Express 4 doesn't auto-catch these)
takes down the whole backend process with no application-level log line — only whatever Docker's
`json-file` log driver captured on stdout. `restart: unless-stopped` brings it back up, but
in-flight requests at that instant are dropped silently. Worth a follow-up fix; flagging so it's a
deliberate decision, not a surprise the first time it happens in production.

## 7. Reverse proxy / domain setup — Nginx (VPS host, not containerized)

`docker-compose.yml` binds every container to `127.0.0.1` only (`127.0.0.1:4000:4000`,
`127.0.0.1:3000:3000`, etc.) — **nothing is reachable from outside the VPS without Nginx in
front.** The repo already has a working config at
[`07ps-sales-dashboard-app/docker/nginx.conf`](../07ps-sales-dashboard-app/docker/nginx.conf):
subdomain-based routing (not path-based — backend routes live at root paths like `/tachometer`,
`/admin/etl-runs`, and some collide with frontend page routes, so they can't share one domain with
a path prefix).

```
<domain>              → frontend :3000
api.<domain>           → backend :4000
etl-api.<domain>       → ETL API :5001 (optional, off by default — internal-only unless you
                                          uncomment the block and add auth in front of it)
```

`basePath: '/Dashboard'` (§2) is confirmed active in `next.config.mjs` — the Next.js server itself
404s a bare `/` request and only answers under `/Dashboard`. `docker/nginx.conf` has been updated
to match: the main-domain HTTPS server block now `301`-redirects `/` to `/Dashboard`, and proxies
`/Dashboard` (and everything under it) through to the frontend container unchanged (`proxy_pass`
with no trailing path segment forwards the original request URI as-is, which is exactly what the
basePath-aware Next.js server expects). No further action needed here unless `basePath` is ever
removed from `next.config.mjs`, in which case revert this block to a plain `location /`.

## 8. Verifying a successful deployment

```bash
# 1. Containers healthy
docker compose ps

# 2. Backend health endpoint
curl -sf https://api.<domain>/health && echo

# 3. Frontend loads (root redirects to /Dashboard -- follow it with -L)
curl -sfL https://<domain>/ | head -5

# 4. ETL API reachable (internal only, run from the VPS itself)
curl -sf http://127.0.0.1:5001/health && echo
```

Or use the repo's own script: `bash scripts/health-check.sh <domain>`.

Then, from the dashboard itself:
1. **Log in** with the Admin account created in §4.
2. **Confirm ETL queue is reachable**: Admin → ETL Runs — should not show a "Queue unavailable"
   banner. If it does, `docker compose logs etl-worker`/`redis` first.
3. **Trigger an incremental refresh** from Admin → ETL Runs and confirm it reaches `COMPLETED` (not
   stuck `QUEUED` — that means no worker is consuming; not `FAILED` — check `docker compose logs
   etl-api` for the pipeline's own error).
4. **Confirm the row-level data scope feature** (added and live-verified this session): as Admin,
   open Admin → Role & Permission Management → B2B Director — should show View+Export checked on
   every Sales page, plus a "Customer Group: B2B" data-scope chip. Logging in as a B2B_DIRECTOR
   user should show identical numbers on every page as an unrestricted user explicitly filtered to
   `segmentKeys=1`, and attempting to request a different segment via the URL should 403, not
   silently succeed.
5. **Check for crash-loop symptoms**: `docker compose ps | grep -i restart` — repeated restarts on
   `backend` point at the unhandled-rejection gap in §6.

## 9. Rollback

**App containers** (never touches MySQL — it's external and untouched by any of this):

```bash
docker compose down
git log --oneline -5              # find the last known-good commit or tag
git checkout <previous-commit-or-tag>
docker compose up -d --build
```

**Database**: no automated migration-rollback tooling exists in this repo — migrations `0009`–
`0013` are additive-only (new tables/columns/rows via `CREATE TABLE IF NOT EXISTS`/`INSERT IGNORE`,
nothing destructive), so rolling back application code does not require rolling back schema. If a
bad migration genuinely needs undoing, it's a manual `DROP TABLE`/`ALTER TABLE` — write and test
that by hand against the specific migration in question; there's no reverse-migration script to
run. Take a `mysqldump` backup before applying new migrations in future, as standard practice —
this repo doesn't automate DB backups (flagged as a gap in the pre-deployment audit, not yet acted
on).

**Tag releases going forward** so rollback has a real target:
```bash
git tag -a v1.0.0 -m "First VPS deployment"
git push --tags
```
